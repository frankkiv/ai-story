PART 2 · 它怎麼運作

AI 沒有在學你。
它每次都重讀一遍。

跟 AI 聊得愈久，它好像愈懂你。但模型本身一個位元都沒變。變的是每次送進去的那份 context：系統提示、工具、skills、記憶，還有整段對話紀錄。

每一次請求，都是把這幾層像積木一樣疊起來，整份送給同一個固定的模型。實際送出時從最底層的工具說明開始，你剛打的這一句放在最後，模型讀到這裡，就順著往下寫回答。

01 · 最常見的誤會

「你一直跟它聊，是在訓練它嗎？」不是。

「訓練」跟「使用」是兩件完全不同的事，發生在不同的時間、不同的地方，花的錢差好幾個數量級。

TRAINING · 訓練

由模型公司做，幾個月一次

  • 改了什麼模型的權重（數量極大的參數）
  • 怎麼改用海量資料跑梯度下降，大量 GPU 連續跑上好幾週
  • 結果產出一個新版本的模型
  • 你能做嗎不能。你聊天時不會發生
INFERENCE · 使用（推論）

每按一次送出，就發生一次

  • 改了什麼什麼都沒改，權重是唯讀的
  • 怎麼運作整份 context 轉成 token 送進去，模型一個 token 一個 token 往下接
  • 結果一段輸出。下一輪把它加進 context 再送
  • 你能做嗎能。你能控制的就是 context 裡放什麼

模型本身是無狀態（stateless）的：模型不會記得上一句。會感覺「它記得」，是因為客戶端（App、Claude Code）把整段對話存起來，下一輪連同新訊息一起再送一次。有些 API（例如 OpenAI 的 Responses API）可以由伺服器幫你存對話，但那只是換成伺服器幫你保管紀錄，底層一樣是把歷史接回去、讓模型整段重讀。所謂「讓 AI 愈來愈懂你」，實際上是在改善每次送進去的 context：寫更好的 prompt、整理記憶檔、把常做的流程寫成 skill。這是工程，不是訓練。

白話說AI 像一位記性只有一頓飯長的專家。每次見面，你都把「之前聊過什麼、家裡的狀況、你習慣怎麼做」整本筆記交給他重看一遍。他沒有變聰明，是你的筆記愈寫愈好。

02 · 最新的事從哪來

模型訓練完就不會再變，為什麼還答得出最新的事？

上一段說過，模型是無狀態的：訓練一結束，權重就固定了，你跟它聊再久也不會改。所以它其實不知道訓練之後發生的事。它答得出來，是因為它會判斷「這個我需要查」，請 App 用工具去拿即時資料，把結果放進這一輪的 context，讀完再回答你。

看動畫：模型怎麼決定要不要上網查 →

  1. YOU → APP你問：「2026 世界盃冠軍是誰？」假設這個模型的訓練資料停在 2026 年初，世界盃 6 月才開踢。App 把你的問題連同今天的日期、可用的工具清單（網路搜尋、你接上的 MCP 連接器）一起送給模型。
  2. MODEL它發現自己不知道它學過的資料裡沒有比賽結果，而系統提示裡的日期告訴它：比賽已經結束了。
  3. MODEL → APP它決定呼叫工具它先不回答，而是輸出一段請求：「用網路搜尋查『2026 世界盃 冠軍』」。如果你接了體育比分的 MCP 連接器，它也可能選那個。要不要查、用哪個工具，是模型自己判斷的。
  4. TOOL工具去拿即時資料網路搜尋由 Anthropic 的伺服器代為執行；MCP 工具由 App 去呼叫那個服務。模型本身不會連網。
  5. APP → MODEL結果放進 context，整包再讀一次查到的網頁摘要或比分資料加在這一輪 context 的最後面，模型把整包重新讀一遍。
  6. MODEL → YOU它根據查到的內容回答「冠軍是 ○○ 隊」，通常會附上來源連結。這一輪結束，權重一個數字都沒變；開新對話再問一次，它還是得重新查。
沒有工具的時候

它只能靠截止日以前學到的

如果 App 沒開搜尋、也沒接任何連接器，模型就沒有地方可以查。問世界盃冠軍，好的情況是它說「我的資料停在比賽之前，沒辦法確定」；不好的情況是它照舊資料猜一個，語氣一樣篤定。

判斷方法：回答有沒有附來源連結，或畫面上有沒有出現「正在搜尋」、呼叫了哪個工具。都沒有，就當它是截止日以前的印象，自己再查證，或直接跟它說「請上網查」。

新資訊進到 context 的三種方式
  • 模型自己去查網路搜尋、MCP 連接器。模型判斷需要才呼叫，App 執行，結果放回 context
  • App 每次都放今天的日期、記憶檔、系統提示。模型沒有開口要，App 也會放
  • 你自己貼上文章、檔案、截圖

這三種方式都只放進這一輪的 context，用完就沒了，不會讓模型「學會」。要讓模型本身知道更新的事，唯一的方法是模型公司重新收集資料、訓練出新版本，大約隔幾個月到一年一次；你用的版本換了，知識截止日（knowledge cutoff）才會往後移。

白話說模型像一位在世界盃開踢前就閉關的專家，記憶停在那天。你問他冠軍是誰，他先看一眼日曆，發現比賽早就結束了，就請助理去買報紙；讀完報紙，他才回答你。報紙看完就收走，他的記憶沒有變；下次再問，還得再買一次。

世界盃的例子是示意，冠軍隊名刻意留白。資料來源：Anthropic 模型說明（各模型的訓練資料截止日）、Anthropic〈Web search tool〉文件、Model Context Protocol 文件。

03 · 一次請求長什麼樣子

你打一句「幫我看這個 bug」，送出去的是一整包

以 Claude Code 為例，每一輪送到 API 的內容依序是這幾層（Anthropic 的 cache 依序比對 tools、system、messages 這三段的前綴）。順序很重要，下一節的 cache 會用到。

看動畫：這一包在你的電腦上怎麼組合、怎麼送出去 →

  1. Tools 定義每個工具的名稱、說明、JSON schema。MCP server 提供的工具也在這裡，工具一多可以上萬 token。Anthropic 的 cache 前綴就是從這層開始算。
  2. System prompt模型是誰、規則、環境資訊。每輪都一樣。
  3. Skills 清單接在系統規則之後送進去，只有每個 skill 的名稱和一句描述，全文用到時才載入。Claude Code 實際把它放在哪一段，隨版本變過。
  4. 記憶檔CLAUDE.md、專案規範、你的偏好。Claude Code 開工時把它讀進來，放在對話最前面的訊息裡。
  5. 對話紀錄之前每一句 user / assistant 訊息、每次工具呼叫和結果，原樣附上。
  6. 這一輪的新訊息你剛打的那句。整包裡常常只有它是新的。

POST /v1/messages（簡化）JSON

  "tools": [ // 每個工具的 schema（cache 比對從這裡開始）

    各家怎麼壓縮？做法其實不一樣

    模型本身不管「對話太長」這件事，壓縮是客戶端（或 API 服務）自己決定的策略，所以每家都不同。上面模擬器的「壓縮方式」可以切換三種做法，看 context 怎麼變。

    工程細節：各種工具的壓縮做法比較
    工具什麼時候壓怎麼壓壓完留下什麼
    Claude Code快滿時自動（約九成，會先扣掉留給輸出的空間）；也能手動打 /compact，後面加上要保留的重點分層：先不用模型，把舊的工具結果清成一行「已清除」；還不夠，才請模型寫結構化摘要摘要（目標、改過的檔案、錯誤、待辦、你說過的話等）＋重新讀回最近改過的檔案；CLAUDE.md 不會被摘要掉，壓縮後客戶端從硬碟重新讀進來，放回對話開頭
    OpenAI Codex CLI約九成時自動；手動 /compact請模型寫一則「交接摘要」；用 Codex 模型時，可以交給伺服器的 compact API，回傳一段加密內容你最近說過的話保留原文（有 token 上限，太舊的會被截掉）；AI 的回覆和工具結果換成那則摘要
    Gemini CLI預設用到一半左右就壓（可調）；手動 /compress先寫摘要，再請模型自己檢查一次有沒有漏最近約 30% 的對話原文＋較舊部分的摘要
    OpenCode約 96%–99% 才壓先剪掉舊的工具輸出，不夠再寫摘要最近約 4 萬 token 的工具輸出、最後兩輪你的訊息
    Anthropic API 的 context editing開發者自己設定門檻伺服器端自動把舊的工具結果清掉，不寫摘要對話結構不變，只是舊工具結果變成「已清除」
    Anthropic API 的 compaction（beta）開發者手動要求，或設定 token 門檻自動觸發伺服器端請 Claude 把較舊的回合寫成摘要一段摘要，加上之後的對話
    共同的代價

    cache 會失效一次

    壓縮等於改寫了對話歷史，下一次請求只有最前面的 tools、system 還能命中 cache，後面要重新寫入。所以壓縮不是愈常做愈好。

    取捨

    早壓還是晚壓？

    早壓（像 Gemini CLI）每次送得少、比較省，但摘要次數多，細節流失也多；晚壓（像 OpenCode）保留最多原文，但快滿時模型的注意力已經被稀釋。

    實用建議

    換題目就開新對話

    壓縮是不得已的補救。做完一件事、要換下一件時，直接開新 session，再讓 AI 讀 CLAUDE.md 或 spec 文件，通常比壓縮後繼續聊乾淨。

    白話說聊太久，筆記本寫滿了。有人把舊頁撕掉、只留重點（Claude Code）；有人留下你最近說過的話、其他的濃縮成一張交接單（Codex）；有人寫完重點還再對一次有沒有漏（Gemini）。哪種都會丟掉一些細節。

    門檻與細節會隨版本改變。Claude Code 的內部做法來自社群的分析文章（它不是開源的），其餘參考各工具的說明文件與 2026 年 4 月的比較文章（Daniel Vaughan〈Context Compaction Showdown〉、Justin3go〈Context Compaction in Codex, Claude Code, and OpenCode〉）。

    05 · Prompt cache

    既然每次都重送，為什麼不會慢到不能用？

    因為模型那一端會把「算過的前綴」暫存起來。下次送來的 context 開頭一模一樣，就直接接著算。

    看動畫：快取在伺服器的哪一步發生 →

    快取的是什麼

    讀到一半的中間狀態

    模型讀 context 時，每個 token 都會算出一組內部狀態（KV cache）。Prompt caching 把這組狀態在伺服器上留一段時間。存的是「讀過這段文字之後的狀態」，不是模型學到了什麼。

    命中條件

    前綴必須逐字相同

    從頭開始比對，中間只要有一個字不同，後面全部失效。所以不常變的東西（tools、system、skills 清單）放最前面，每輪都變的對話放最後面。改一個工具定義，整串 cache 就要重建。

    時效與價格

    預設 5 分鐘，讀取約 1 折

    Anthropic API 的 cache 預設存活 5 分鐘，每次命中重新計時，也可以選 1 小時。讀取約是一般 input 價格的 10%，寫入稍貴。離開太久再回來，第一輪要整包重算。Claude Code 用訂閱方案、還在方案額度內時，主對話預設改用 1 小時。

    白話說像餐廳記得你是熟客：五分鐘內再點，廚房不用重新備料。記得的只是「備好的料」，廚師的手藝一點都沒變。

    06 · Agent 迴圈

    「AI 自己動手」其實是一個 while 迴圈

    模型不會真的執行任何東西。它只會輸出「我想呼叫這個工具，參數是這些」。真正執行的是你電腦上的客戶端，執行完把結果塞回 context，再問模型一次。

    看動畫：模型怎麼決定要不要上網查、工具在哪裡跑 →

    1. USER → CLIENT你說「修好登入的 bug」客戶端把它加到對話紀錄最後面。
    2. CLIENT → MODEL送出整份 contextsystem + tools + 歷史 + 新訊息。
    3. MODEL → CLIENTstop_reason: tool_use模型回「我要 Read auth.ts」。它沒有讀，只是提出請求。
    4. CLIENT在你電腦上執行工具讀檔、跑指令、呼叫 MCP server。需要時先問你同不同意。
    5. CLIENT → MODEL附上 tool_result 再送一次context 又變長了。回到第 3 步，直到模型不再要工具。
    6. MODEL → USERstop_reason: end_turn最後回覆：「修好了，改了兩個地方，測試都過。」
    工程細節：迴圈的虛擬碼
    agent loop（虛擬碼）python
    messages.append(user("修好登入的 bug"))
while True:
    resp = model.create(system, tools, messages)  # 整包重送
    messages.append(resp)                         # 存回本地紀錄
    if resp.stop_reason != "tool_use":
        break                                     # 做完了
    result = run_tool_locally(resp.tool_use)      # 客戶端執行
    messages.append(tool_result(result))
    這幾年很多進化，都發生在這個迴圈上
    • MCP工具定義的標準格式，任何 server 都能接進 tools 那一層
    • Subagent另開乾淨的 context 跑子任務，只帶摘要回來，主 context 不會被塞爆
    • Compactioncontext 快滿時，把舊對話摘要成一段換掉原文
    • Remote迴圈跑在你電腦或雲端，手機只是看紀錄、送新訊息
    07 · AI IDE 的 Auto 模式

    「Auto」其實有兩種：自動選模型，跟自動按「允許」

    Cursor、Claude Code 這些工具都有個 Auto 開關，但背後是兩件不同的事。它們的共同點是：都另外放了一個比較小、比較快的模型，專門在旁邊做判斷。主模型本身沒有變。

    第一種 · 自動選模型

    Cursor Auto：每一句話都先分類，再派給合適的模型

    1. 你送出一個請求例如「把這個變數改名」或「重構整個登入流程」。
    2. 路由分類器先看一眼判斷任務類型和難度。Cursor 2026 年 7 月推出的 Cursor Router，就是一個專門做這件事的分類器。
    3. 派給對應的模型簡單的給便宜快速的模型，難的給 Opus、Fable 這類大模型。可以選偏省錢（Cost）、平衡（Balance）或偏聰明（Intelligence）。

    Cursor 自己的說法是：比全部都用 Opus 4.8 便宜三到五成。這是廠商數字，沒有第三方驗證。

    第二種 · 自動核准動作

    Claude Code auto mode：每個動作執行前，先過一道安檢

    1. 分三級只讀檔案的工具直接放行；改專案裡的檔案也放行；其他動作（跑指令、上網、碰專案外的檔案）都要過分類器。
    2. 分類器只看兩樣東西你說過的話，和 AI 準備執行的那個動作。AI 自己的解釋和工具回傳的內容都不給它看，避免被說服或被網頁裡藏的指令影響。
    3. 兩段檢查先快速判斷「可不可以」，寧可多擋；被擋下的再仔細推理一次，減少誤擋。
    4. 被擋了怎麼辦AI 會收到「這個不行」，改找安全的做法。連續被擋 3 次或總共 20 次，就停下來問你。

    預設擋下的有二十多類，例如強制覆蓋 git 紀錄、大量刪檔、搜集密碼金鑰、把程式碼分享到外部。另外還有一層會先掃描工具讀回來的內容，看有沒有 prompt injection。

    數字

    擋得準嗎？

    Anthropic 公布的測試：真實使用中，正常動作被誤擋的比例約 0.4%；但 AI「太積極」做出的越界動作，仍有約 17% 沒擋到。所以它是減少打擾的工具，不是保險。

    跟前面的關係

    還是同一個 agent 迴圈

    Auto 模式沒有改變迴圈本身：模型一樣輸出 tool_use，只是「要不要問你」這一步，從每次跳視窗變成交給分類器判斷。

    要注意

    成本和責任都還在你身上

    自動選模型可能在你不知道的情況下用了比較貴的模型；自動核准則代表你不會看到每一步。重要的專案，還是先在測試環境跑。

    白話說自動選模型像總機，聽完你的問題，轉給最適合的師傅；自動核准像門口的警衛，照清單判斷哪些事可以直接做，可疑的就攔下來問屋主。

    來源：Anthropic Engineering〈Claude Code auto mode〉（2026/3/25）；Cursor 說明文件〈Available models〉與 Cursor Router 發表報導（2026/7）。

    08 · 手機跟電腦怎麼同步

    同一個帳號，資料其實放在三個不同的地方

    「在手機上接著做」看起來像魔法，其實要先分清楚：這段對話存在哪？迴圈在哪台機器上跑？手機只是哪一種遙控器？

    看動畫：手機訊息怎麼經過中繼交給電腦 →

    你的手機 / 網頁

    Claude App、claude.ai/code

    • 顯示對話、送出新訊息
    • 按允許／拒絕工具權限
    • 不執行任何程式、沒有你的檔案
    TLS
    Anthropic API（中繼）

    帳號、對話紀錄、訊息轉送

    • 一般聊天的對話紀錄存在這裡，所以每台裝置看到的清單都一樣
    • Remote Control 連線期間，transcript 也會存在這裡
    • 用串流連線把兩端的訊息互相轉送
    只往外連
    你的電腦

    本地的 Claude Code

    • agent 迴圈在這裡跑
    • 讀檔、跑指令、MCP 工具都在這裡執行
    • 只發出 HTTPS 連線、不開任何對外 port；關機或程式結束，手機那頭就離線
    用法對話紀錄存在程式在哪跑手機能做什麼
    一般聊天（App／網頁）Anthropic 伺服器，跟著帳號走只有模型推論，沒有你的電腦完整使用，換裝置接著聊
    本地 Claude Code你電腦的 ~/.claude/projects/你的電腦不能，紀錄沒離開電腦
    Remote Control本地一份；連線期間伺服器也存一份你的電腦（要保持開機）看進度、下指令、批准權限
    雲端 session（Claude Code on the web）Anthropic 伺服器Anthropic 管理的雲端容器從手機開工，電腦可以關

    不管哪一種，模型本身都不存任何東西。所謂「同步」，同步的是對話紀錄和訊息，下一輪照樣是把整份 context 重送一次。

    白話說手機像電視遙控器，電腦是電視。遙控器按的訊號先送到 Anthropic 的「轉接站」，再轉給家裡的電腦。所以電腦要開著；檔案也一直留在家裡。

    09 · 多 Agent 協作

    從 BMAD 到 Projects：一個 AI 怎麼管好幾個 AI

    一個 agent 迴圈做小任務很好用。但大專案要規劃、寫程式、測試、審查，全塞在同一個 context 裡很快就滿，一個角色也很難樣樣顧到。過去兩年，工程師的解法從「自己寫指揮系統」，一路走到「工具直接內建」。

    2024–2025 · 自己搭

    工程師自製 orchestrator

    用腳本或 LangGraph、CrewAI、AutoGen 這類框架，把多次模型呼叫串起來：一個拆任務、幾個動手做、最後一個檢查。彈性最大，但狀態怎麼存、失敗怎麼重試、誰能看到什麼，全都要自己寫。

    2025 · 用文件交接

    BMAD-METHOD

    開源方法論（Breakthrough Method for Agile AI-Driven Development）。把 AI 分成 Analyst、PM、Architect、Scrum Master、Dev、QA 等角色，每個角色是一份 Markdown 設定。規劃階段寫出 PRD 和架構文件，Scrum Master 再切成一張張 story 檔，Dev 一次只做一張。交接全靠 Git 裡的檔案，每個角色只載入自己需要的文件。

    2025–2026 · 工具內建

    Subagents，然後是 Projects

    Claude Code 先加入 subagents：主 agent 把子任務交給一個有獨立 context 的小 agent，做完只回傳結果。2026 年 9 月 17 日推出的 Projects（beta）更進一步：直接由一個 Claude 管理好幾個並行的完整 session。

    工程細節：Projects 怎麼運作、三種做法比較
    Projects 怎麼運作

    一個總機，加上很多條各做各的 thread

    1. 你只跟專案對話講話那裡的 Claude 是協調者。它判斷一則訊息要自己回答，還是開一條新的 thread 去做。
    2. 每條 thread 是獨立的 session有自己的 context window 和雲端容器，會 clone 專案裡的 repo，在自己的分支上工作，需要時開 PR。五件事同時做，context 也不會互相塞爆。
    3. 做完回報thread 在自己的串裡回覆你。協調者看得到每條 thread 的回覆，你後來補充的要求，它會把你的原話附上轉交，而不是自己轉述。
    4. 需要時回到你的電腦thread 可以透過 Remote Control 在你的電腦上跑，用你本機的工具和登入狀態（電腦要開著）。9/17 推出時官方說「很快會支援」，9 月底起文件已列為可用。這個網站推上 GitHub，就是這樣做的。
    怎麼溝通、共享什麼

    大部分訊息都經過協調者

    1. 共用的東西專案的 repo、檔案區（Library）、專案記憶和指示、連接器。新開的 thread 一開始就帶著這些。
    2. thread 之間很少直接講話只有工作彼此相依時才互傳訊息，其餘都透過協調者。這樣可以避免一群 AI 互相聊天、白白燒掉額度。
    3. 誰的話算數有標記只有你本人寫的訊息能算「同意」。其他 AI 傳來的訊息只當參考，不能替你按下 push、刪檔這類收不回的動作。
    4. 有事才醒來thread 平常不跑。你的新訊息、PR 上的留言、CI 失敗，這些事件會把它叫醒處理。
    做法誰分派工作怎麼交接context 怎麼隔開你要維護什麼
    自製 orchestrator你寫的程式程式裡的變數、佇列看你怎麼寫全部
    BMAD你照流程切換角色（或交給它的 Orchestrator 角色）Git 裡的 PRD、架構文件、story 檔每個角色只載入需要的文件角色設定與模板
    Claude Code Projects協調者 Claudethread 回報、附原話轉交、共用檔案與記憶每條 thread 是獨立 session專案指示、記憶、repo 裡的 spec
    要注意

    額度燒得比較快

    每條 thread 都是完整的 session，協調者本身也在用 token，所以同樣的方案額度會用得比較快。每天新開的 thread 也有上限：官方文件寫的是所有專案合計 200 條。

    還是 beta

    功能可能隨時改

    2026 年 9 月先開放給部分 Pro、Max 用戶，逐步擴大。Team、Enterprise 方案和終端機版 CLI 還不能用。

    跟 BMAD 一樣

    文件還是關鍵

    接手的 AI 不記得過去，靠的是 repo 裡的 CLAUDE.md、spec 文件和專案記憶。這也是這個網站的 repo 裡有 docs/SPEC.md 的原因。

    白話說以前像自己當工頭，排班、傳話、記進度都自己來；BMAD 是一套「交接單」制度，每個師傅只看自己那張單；Projects 則是請了一位總管，你只跟總管說，總管開工單給不同師傅，師傅做完回報，重要的事還是要你點頭。

    來源：BMAD-METHOD 開源專案與介紹文章；Claude Code Projects 文件（code.claude.com/docs/en/claude-projects）與 2026 年 9 月的發表報導。thread 之間怎麼溝通，部分來自實際用 Projects 做這個網站時的觀察，beta 期間可能調整。

    10 · 記憶與 Skills

    「愈用愈順手」靠的是本地的文字檔

    跟 AI 磨合出來的東西，最後都落在你電腦上的幾個檔案裡。下次開工時被讀進 context，所以它看起來「學會了」。

    工程細節：這些檔案放在哪、skill 檔長什麼樣子
    你的專案與家目錄tree
    my-project/
├── CLAUDE.md              # 專案規範，每次開工都讀
└── .claude/skills/
    └── release-notes/
        ├── SKILL.md           # 名稱、描述、步驟
        └── template.md

~/.claude/
├── CLAUDE.md              # 你個人的偏好
└── projects/…/*.jsonl    # 每段對話的完整紀錄
    .claude/skills/release-notes/SKILL.mdmd
    ---
name: release-notes
description: 從 git log 產生給使用者看的版本說明
---
1. 讀上一個 tag 之後的 commit
2. 依「新功能 / 修正 / 其他」分類
3. 用 template.md 的格式輸出
4. 不要列出內部重構   # ← 上週聊完補上的
    漸進載入

    平常只占幾十個 token

    context 裡只放每個 skill 的 name 和 description。模型判斷這次用得到，才去讀 SKILL.md 全文和附檔。所以 skill 可以裝很多，不會撐爆 context。

    怎麼「精進」

    聊天時發現問題，就改檔案

    輸出列了不該列的東西，你說「以後不要列內部重構」。把這句寫回 SKILL.md，下次任何對話載入它，都會照新規則做。

    重點

    這是 prompt 工程，不是訓練

    改的是文字檔，可以 diff、可以 git commit、可以分享給同事。換一版模型，skill 照樣能用。權重從頭到尾沒動過。

    白話說我們不是在把 AI「教聰明」，是在幫它寫一本愈來愈好的工作手冊。手冊放在我們自己的電腦裡，每次叫它做事，就先把相關的那幾頁翻給它看。
