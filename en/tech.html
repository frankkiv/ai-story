PART 3 · How it works

AI isn't learning you.
It rereads everything, every time.

The longer you chat with AI, the better it seems to know you. But not a single bit of the model has changed. What changes is the context sent in each time: the system prompt, tools, skills, memory, and the whole conversation so far.

01 · The most common myth

"Am I training it by chatting with it?" No.

"Training" and "using" are completely different things. They happen at different times, in different places, and their costs differ by orders of magnitude.

TRAINING

Done by the model company, every few months

  • What changesThe model's weights (an enormous number of parameters)
  • HowGradient descent over massive data, on huge numbers of GPUs running for weeks
  • ResultA new version of the model
  • Can you do it?No. It doesn't happen while you chat
INFERENCE · Using it

Happens every time you press send

  • What changesNothing. The weights are read-only
  • How it worksThe whole context is turned into tokens and fed in; the model continues one token at a time
  • ResultSome output. Next round, it's added to the context and sent again
  • Can you do it?Yes. What you control is what goes into the context

The model itself is stateless: the API doesn't remember your previous message. It feels like "it remembers" because the client (the app, Claude Code) saves the whole conversation and sends it again with your new message. "Making AI understand you better" really means improving the context sent in each time: better prompts, a tidier memory file, common workflows written as skills. That's engineering, not training.

In plain wordsAI is like an expert whose memory lasts one meal. Every time you meet, you hand over your whole notebook (what you talked about before, your home situation, how you like things done) for them to reread. They didn't get smarter; your notebook got better.

02 · What one request looks like

You type "look at this bug", and a whole bundle goes out

Taking Claude Code as the example, each round sends these layers to the API, in this order (Anthropic's cache matches prefixes in tools → system → messages order). The order matters; the cache section uses it.

  1. Tool definitionsEach tool's name, description and JSON schema. Tools from MCP servers are here too; with many tools this can be tens of thousands of tokens. Anthropic's cache prefix starts from this layer.
  2. System promptWho the model is, the rules, environment info. The same every round.
  3. List of skillsInside the system prompt: just each skill's name and a one-line description. The full text loads only when needed.
  4. Memory fileCLAUDE.md, project conventions, your preferences. Claude Code reads it at the start and puts it in the first message of the conversation.
  5. Conversation historyEvery earlier user and assistant message, every tool call and result, attached as is.
  6. This round's new messageWhat you just typed. Often it's the only new thing in the whole bundle.

{
  "model": "claude-…",
  "tools": [ // each tool's schema (cache matching starts here)
    { "name": "Read", "input_schema": { … } },
    { "name": "Bash", "input_schema": { … } }
  ],
  "system": [ // rules + list of skills
    { "type": "text", "text": "You are Claude Code…",

    { "role": "user",      "content": "look at this bug" },

    { "role": "assistant", "content": "The problem is on line 42…" },
    { "role": "user",      "content": "OK, fix it" }  // ← new
  ]

    How does each tool compact? It's different everywhere

    The model doesn't deal with "the conversation is too long". Compaction is a strategy the client (or API service) decides on, so every vendor does it differently. Switch "Compaction style" in the simulator above to see how three approaches change the context.

    ToolWhen it compactsHowWhat's left afterwards
    Claude CodeAutomatically when nearly full (around 90%, after reserving room for output); or manually with /compact, followed by what to keepIn layers: first, without the model, old tool results are cleared to a one-line "cleared"; if that's not enough, the model writes a structured summaryThe summary (goals, files changed, errors, to-dos, what you said, etc.) plus the most recently edited files read back in; CLAUDE.md is in the system prompt and unaffected
    OpenAI Codex CLIAutomatically at around 90%; manually with /compactThe model writes a "handoff summary"; with Codex models this can go to the server's compact API, which returns encrypted contentEverything you said, verbatim; the AI's replies and tool results are replaced by that summary

    OpenCodeOnly at about 96%–99%First prunes old tool output, then summarizes if still neededThe last ~40,000 tokens of tool output and your last two turns
    Anthropic API context editingA threshold the developer setsThe server automatically clears old tool results, with no summaryThe conversation's structure is unchanged; old tool results just become "cleared"
    The shared cost

    The cache misses once

    Compaction rewrites the conversation history, so the next request can only hit the cache for the tools and system at the front; the rest is written again. So compacting more often isn't better.

    The trade-off

    Compact early or late?

    Compacting early (like Gemini CLI) sends less each time and costs less, but summarizes more often and loses more detail. Compacting late (like OpenCode) keeps the most original text, but by the time it's nearly full, the model's attention is already diluted.

    Practical tip

    New topic, new conversation

    Compaction is a last resort. When one task is done and you're moving to the next, start a new session and have the AI read CLAUDE.md or the spec docs. That's usually cleaner than continuing after a compaction.

    In plain wordsChat too long and the notebook fills up. One approach tears out old pages and keeps the highlights (Claude Code); another keeps every word you said and condenses the rest into a handoff note (Codex); another writes the highlights and then double-checks for anything missed (Gemini). Every approach loses some detail.

    Thresholds and details change between versions. Claude Code's internals come from community analysis (it isn't open source); the rest draws on each tool's documentation and April 2026 comparison articles (Daniel Vaughan, "Context Compaction Showdown"; Justin3go, "Context Compaction in Codex, Claude Code, and OpenCode").

    04 · Prompt cache

    If everything is resent each time, why isn't it unbearably slow?

    Because the model's side keeps the "already computed prefix" for a while. If the next context starts exactly the same, it picks up from there.

    What's cached

    An intermediate state, halfway through reading

    As the model reads the context, each token produces a set of internal state (the KV cache). Prompt caching keeps that state on the server for a while. It stores "the state after reading this text", not anything the model learned.

    When it hits

    The prefix must match exactly

    Matching starts from the beginning; one character different and everything after it is invalid. So things that rarely change (tools, system, the skills list) go first, and the conversation that changes every round goes last. Change one tool definition and the whole cache has to be rebuilt.

    Lifetime and price

    5 minutes by default, reads at about 10%

    Anthropic's cache lives 5 minutes by default, resetting on each hit, with a 1-hour option. Reads cost about 10% of the regular input price; writes cost a bit more. Step away too long and the first round has to recompute everything.

    In plain wordsLike a restaurant that recognizes a regular: order again within five minutes and the kitchen doesn't have to prep from scratch. What it remembers is the prepped ingredients; the chef's skill hasn't changed at all.

    05 · The agent loop

    "AI doing things itself" is really a while loop

    The model never actually runs anything. It only outputs "I want to call this tool with these arguments". The client on your computer runs it, puts the result back into the context, and asks the model again.

    1. USER → CLIENTYou say "fix the login bug"The client appends it to the end of the conversation.
    2. CLIENT → MODELSend the whole contextsystem + tools + history + new message.
    3. MODEL → CLIENTstop_reason: tool_useThe model replies "I want to Read auth.ts". It didn't read anything; it only asked.
    4. CLIENTRun the tool on your computerRead files, run commands, call MCP servers. Ask you for permission when needed.
    5. CLIENT → MODELSend again with the tool_resultThe context grows again. Back to step 3, until the model stops asking for tools.
    6. MODEL → USERstop_reason: end_turnFinal reply: "Fixed it. Changed two places, tests pass."
    agent loop (pseudocode)python
    messages.append(user("fix the login bug"))
while True:
    resp = model.create(system, tools, messages)  # resend everything
    messages.append(resp)                         # save to local history
    if resp.stop_reason != "tool_use":
        break                                     # done
    result = run_tool_locally(resp.tool_use)      # the client runs it
    messages.append(tool_result(result))
    Much of the progress in recent years happened in this loop
    • MCPA standard format for tool definitions; any server can plug into the tools layer
    • SubagentRuns a subtask in a fresh context and brings back only a summary, so the main context doesn't overflow
    • CompactionWhen the context is nearly full, old conversation is summarized and the summary replaces the original
    • RemoteThe loop runs on your computer or in the cloud; the phone just views the history and sends new messages
    06 · Auto modes in AI IDEs

    "Auto" means two things: picking the model, and pressing "Allow" for you

    Tools like Cursor and Claude Code have an Auto switch, but behind it are two different things. What they share: both add a smaller, faster model on the side just to make judgment calls. The main model itself is unchanged.

    Type 1 · Automatic model choice

    Cursor Auto: classify each request, then send it to a suitable model

    1. You send a requestSay, "rename this variable" or "refactor the whole login flow".
    2. A routing classifier takes a look firstIt judges the task type and difficulty. Cursor Router, launched by Cursor in July 2026, is a classifier built just for this.
    3. It goes to the matching modelSimple ones go to cheap, fast models; hard ones to big models like Opus or Fable. You can lean toward Cost, Balance or Intelligence.

    Cursor's own claim: 30–50% cheaper than using Opus 4.8 for everything. That's a vendor number, not independently verified.

    Type 2 · Automatic approval

    Claude Code auto mode: every action goes through a security check first

    1. Three tiersRead-only tools go straight through; editing files inside the project goes through too; everything else (running commands, going online, touching files outside the project) goes through the classifier.
    2. The classifier sees only two thingsWhat you said, and the action the AI is about to take. It doesn't see the AI's own explanations or tool output, so it can't be talked into things or swayed by instructions hidden in web pages.
    3. Two-stage checkA quick "allowed or not" first, erring on the side of blocking; anything blocked is then reasoned through more carefully to reduce false blocks.
    4. What happens when it's blockedThe AI is told "not allowed" and looks for a safe alternative. After 3 blocks in a row or 20 in total, it stops and asks you.

    Over twenty categories are blocked by default, such as force-overwriting git history, mass deletions, harvesting passwords and keys, and sharing code externally. Another layer also scans what tools read back for prompt injection.

    Numbers

    How accurate is it?

    Anthropic's published tests: in real use, about 0.4% of normal actions get wrongly blocked; but about 17% of overreaching actions by an "overeager" AI still get through. So it's a tool for fewer interruptions, not insurance.

    How it relates

    Still the same agent loop

    Auto mode doesn't change the loop itself: the model still outputs tool_use; only the "should we ask you?" step moves from a pop-up every time to the classifier's judgment.

    Watch out

    The cost and the responsibility are still yours

    Automatic model choice may use a pricier model without you knowing; automatic approval means you won't see every step. For important projects, try it in a test environment first.

    In plain wordsAutomatic model choice is like a switchboard operator who listens to your question and puts you through to the right specialist; automatic approval is like a guard at the door who follows a checklist, letting routine things through and stopping anything suspicious to ask the homeowner.

    Sources: Anthropic Engineering, "Claude Code auto mode" (2026/3/25); Cursor docs, "Available models", and coverage of the Cursor Router launch (2026/7).

    07 · How phone and computer stay in sync

    One account, but the data lives in three different places

    "Picking up on your phone" looks like magic, but first sort out: where is this conversation stored? Which machine runs the loop? What kind of remote is the phone?

    Your phone / the web

    Claude app, claude.ai/code

    • Shows the conversation and sends new messages
    • Lets you allow or deny tool permissions
    • Runs no code and has none of your files
    TLS
    Anthropic API (relay)

    Account, conversations, message relay

    • Regular chat history is stored here, so every device sees the same list
    • While Remote Control is connected, the transcript is stored here too
    • A streaming connection relays messages between the two ends
    outbound only
    Your computer

    Local Claude Code

    • The agent loop runs here
    • Reading files, running commands and MCP tools all happen here
    • Only makes outbound HTTPS connections and opens no inbound ports; shut down the computer or quit the program and the phone goes offline

    In plain wordsThe phone is a TV remote and the computer is the TV. The remote's signal goes to Anthropic's "relay station" first, then on to the computer at home. So the computer has to be on, and the files always stay at home.

    08 · Multi-agent teamwork

    From BMAD to Projects: how one AI manages several AIs

    One agent loop is great for small tasks. But a big project needs planning, coding, testing and review, and cramming it all into one context fills it fast; one role also can't cover everything well. Over the past two years, engineers' answer went from "build your own orchestration system" to "it's built into the tool".

    2024–2025 · Build your own

    Homegrown orchestrators

    Engineers chained model calls together with scripts or frameworks like LangGraph, CrewAI and AutoGen: one splits the task, a few do the work, a final one checks it. Maximum flexibility, but how state is saved, how failures are retried and who can see what all have to be written yourself.

    2025 · Hand off with documents

    BMAD-METHOD

    An open-source methodology (Breakthrough Method for Agile AI-Driven Development). It splits the AI into roles such as Analyst, PM, Architect, Scrum Master, Dev and QA, each defined by a Markdown file. The planning phase produces a PRD and an architecture doc; the Scrum Master then cuts them into story files, and Dev works on one at a time. Handoffs happen entirely through files in Git, and each role loads only the documents it needs.

    2025–2026 · Built into the tool

    Subagents, then Projects

    Claude Code first added subagents: the main agent hands a subtask to a small agent with its own context, which returns only the result. Projects (beta), launched on September 17, 2026, goes further: one Claude directly manages several full sessions running in parallel.

    How Projects works

    One switchboard, plus many threads each doing their own job

    1. You only talk to the project chatThe Claude there is the coordinator. It decides whether to answer a message itself or start a new thread to do the work.
    2. Each thread is its own sessionWith its own context window and cloud container, it clones the project's repos, works on its own branch, and opens a PR when needed. Five things can run at once without their contexts crowding each other.
    3. Report back when doneA thread replies to you in its own thread. The coordinator sees every thread's replies, and when you add a follow-up, it forwards your exact words rather than paraphrasing them.
    4. Back to your computer when neededA thread can run on your computer through Remote Control, using your local tools and sign-ins. That's how this website was pushed to GitHub.
    How they communicate, what they share

    Most messages go through the coordinator

    1. Shared thingsThe project's repos, file area (Library), project memory and instructions, and connectors. A new thread starts with all of these.
    2. Threads rarely talk directlyThey message each other only when their work depends on each other; everything else goes through the coordinator. That keeps a crowd of AIs from chatting among themselves and burning through usage.
    3. Whose words count is labeledOnly messages you wrote yourself count as "approval". Messages from other AIs are just information; they can't press push or delete files for you.
    4. Wake up only when something happensThreads don't run idle. Your new message, a comment on a PR, or a failing CI run wakes them up.

    Watch out

    It burns through usage faster

    Every thread is a full session, and the coordinator uses tokens too, so the same plan's limits get used up faster. There's also a daily cap on new threads.

    Still in beta

    Things may change at any time

    Opened to some Pro and Max users in September 2026, expanding gradually. Team and Enterprise plans and the terminal CLI can't use it yet.

    Same as BMAD

    Documentation is still key

    The AI that picks up the work doesn't remember the past; it relies on CLAUDE.md, spec docs and project memory in the repo. That's why this website's repo has docs/SPEC.md.

    In plain wordsIt used to be like being your own foreman: scheduling, passing messages and tracking progress yourself. BMAD is a "work order" system where each tradesperson only reads their own order. Projects is like hiring a site manager: you only talk to the manager, who hands out work orders to different tradespeople, they report back when done, and the important calls still need your OK.

    Sources: the BMAD-METHOD open-source project and introductory articles; the Claude Code Projects documentation (code.claude.com/docs/en/claude-projects) and launch coverage from September 2026.     09 · Memory and Skills

    "It gets easier the more I use it" comes from local text files

    Everything you and the AI work out together ends up in a few files on your computer. They're read into the context the next time you start, so it looks like it "learned".

    Your project and home directorytree
    my-project/
├── CLAUDE.md              # project conventions, read every time
└── .claude/skills/
    └── release-notes/
        ├── SKILL.md           # name, description, steps
        └── template.md

~/.claude/
├── CLAUDE.md              # your personal preferences
└── projects/…/*.jsonl    # full record of each conversation
    .claude/skills/release-notes/SKILL.mdmd
    ---
name: release-notes
description: Generate user-facing release notes from git log
---
1. Read the commits since the last tag
2. Group them into new features / fixes / other
3. Output in the format of template.md
4. Don't list internal refactors   # ← added after last week's chat
    Progressive loading

    Usually just a few dozen tokens

    The context holds only each skill's name and description. Only when the model decides it needs one does it read the full SKILL.md and attached files. So you can install many skills without overflowing the context.

    How it "improves"

    Chat → spot a problem → edit the file

    The output listed something it shouldn't, so you say "don't list internal refactors from now on". Write that line back into SKILL.md, and any future conversation that loads it follows the new rule.

    The point

    This is prompt engineering, not training

    What changes is a text file: you can diff it, git commit it and share it with colleagues. Switch to a new model version and the skill still works. The weights were never touched.

    In plain wordsWe're not "teaching AI to be smarter"; we're writing it an ever-better work manual. The manual lives on our own computer, and every time we ask it to do something, we flip it open to the relevant pages first.
